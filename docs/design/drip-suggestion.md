# 次枠キュー・シフト管理 設計書

## 概要

ドリップ係向け画面と、次にセットするバッチを決めるアルゴリズムの設計方針。

### 基本方針

- **効率と公平性の両立**: 古い注文を後回しにしない公平性を担保しつつ、ドリッパーのバッチ処理による効率化を両立する
- **待ち時間の抑制を優先**: 本機能の目的は客の待ち時間の抑制。長く待っている注文は優先して対応予定に割り当てる
- **役割の特化**: ドリップ係画面は「現在抽出中のもの」を除外し、**「次に 3 台のドリッパーへセットすべき予定（次枠バッチ群）」の確認と準備に特化**させる
- **全端末で同じ提案**: 3 人のドリップ係が同じキューを見る。キューはサーバー（OrderDO）で一元管理する
- **操作数を少なくする**: ドリップ係の操作を増やす確認ダイアログなどは設けない
- **既存資産の活用**: 未対応杯数の計算や抽出開始のトリガーは、既存の注文・抽出記録（`brew_units`）と連携する

---

## 前提（物理仕様とデータ構造）

- **管理対象**: 抽出中のコーヒーは別で管理しているため、**「次のドリッパー枠（最大 3 台分の次期バッチ群）」のみ**をキューとして管理する
- **バッチの単位**: 1 バッチ = 1 台のドリッパーで抽出する「1 種類 × 最大 3 杯」の塊。キューには最大 3 つ並ぶ
- **ドリッパーとの対応**: キューのエントリーは特定のドリッパーに対応させない。空いたドリッパーの担当者が抽出を開始する
- **メニュー**: コーヒーは 1 種類以上。営業開始時点で `is_available = 1` の全メニューを対象とし、営業途中の追加・変更は行わない

---

## 用語

| 用語 | 意味 |
|------|------|
| 対象メニュー | 営業開始時点で `is_available = 1` のコーヒー |
| メニュー順 | 登録日時（`created_at`）の昇順、同時刻なら `id` の昇順。同点時の最終決定に使う |
| エントリー | キュー内の 1 バッチ（種類・杯数） |
| 未対応杯数 | 注文の杯数から、完成（紐付き済み）・抽出中・対応予定の杯を差し引いた残り |
| 対応予定 | キューに表示中のエントリーの杯 |
| 最も古い注文 | 未対応杯数が 1 杯以上残っている注文のうち、最も古い注文 |
| 古い 3 注文 | 未対応杯数が 1 杯以上残っている注文のうち、古い順の 3 注文 |
| 一致 | 開始した抽出とエントリーの種類・杯数がともに同じこと（A 3 杯に対して A 3 杯は一致、A 2 杯は不一致） |
| 代表注文 | バッチに含まれる杯の割り当て先のうち、最も古い注文 |

---

## 対象メニューの決定

- OrderDO の初期化時に、`is_available = 1` のメニューを **登録日時（`created_at`）の昇順、同時刻なら `id` の昇順**ですべて取得する
- 一度決めた対象メニューと順序は営業中に再取得・変更しない
- OrderDO の再起動で入れ替わらないよう、決定したメニュー ID の配列を DO の保存領域（`state.storage`）に保存し、再起動後はそれを使う

---

## キューの管理

### 置き場所

- キューは OrderDO が保持し、DO の保存領域（`state.storage`）に保存する
- キューが変わるたびに WebSocket で全端末へ送信する（例: `QUEUE_UPDATED`）。接続時の `SNAPSHOT` にもキューを含める
- 各端末は受信したキューを表示するだけで、自分では計算しない

### 固定の原則

- 表示中のエントリーの **種類と並びは変えない**
- エントリーの **杯数は増減を認める**（3 杯未満のエントリーへの補充、注文取消による削減）
- エントリーがなくなるのは、消費されたとき、または注文取消で 0 杯になったときのみ
- 新しいエントリーは空いた枠にのみ作り、既存エントリーの後ろ（末尾）に追加する

---

## 未対応杯数の計算

注文を古い順に並べ、各注文の品目ごとに以下の順で差し引く。

```
1. その品目に紐付いた完成品（ready）の杯数を差し引く。
2. 抽出中（brewing）の杯を、メニューごとに古い注文から順に割り当てて差し引く。
3. 対応予定（キューのエントリー）の杯を、メニューごとに古い注文から順に割り当てて差し引く。
4. 残りが未対応杯数。
```

- 抽出中・対応予定の杯は DB 上どの注文にも紐付かないため、古い注文から順に仮に割り当てる（会計係画面の仮想割り当てと同じ考え方）
- 補充のたびにこの計算をやり直す

---

## 補充

### タイミング

以下のとき、キューに空き枠または 3 杯未満のエントリーがあれば補充する。

- 抽出開始（エントリーの消費）
- 新しい注文が入ったとき
- 抽出の取消
- 注文の取消

### 手順

```
1. 未対応杯数を計算し直す。
2. 3 杯未満の既存エントリーに、同じ種類の未対応の杯を古い注文から順に 3 杯まで加える（前のエントリーから）。
3. 空き枠がなければ終了する。
4. 最も古い注文が、注文から「平均抽出時間 × 2」を経過しているか判定する。
5. 経過していれば「長時間待ちの優先」で最初のバッチを決める。
6. 残りの空き枠は「通常時の決め方」で 1 枠ずつ決める。1 枠決めるたびに、その杯を対応予定として差し引いてから次の枠を決める。
7. 今回追加するバッチのみを代表注文の古い順に並べ、既存エントリーの末尾に追加する。
```

### 通常時の決め方

- **種類の選び方**: 古い 3 注文に含まれる種類のうち、**古い 3 注文の中の未対応杯数の合計が最も多い種類**を選ぶ
- **同数の場合**: 同数の候補のいずれかを含む注文のうち、最も古い注文を基準にする。その注文に候補が複数含まれる場合は、その注文の中で杯数が最も多い種類、それも同数ならメニュー順で先の種類を選ぶ
- **バッチの杯数**: 選んだ種類の未対応の杯を、古い注文から順に最大 3 杯入れる（古い 3 注文以外の注文の杯も含めてよい）
- 少数派の種類が後回しになる場合は、「長時間待ちの優先」で対応する

### 長時間待ちの優先

- **条件**: 補充時点で、最も古い注文が注文から「平均抽出時間 × 2」を経過している。平均抽出時間は 3 分弱のため、**5 分以上**経過で適用する
- **対象**: 1 回の補充で条件を満たす注文が複数あっても、最も古い注文の 1 件のみ
- **処理**: 最も古い注文の未対応の杯を最初のバッチにする。3 杯に満たなければ同じ種類で 3 杯まで補充する
- **複数種類ある場合**: 最も古い注文の未対応の杯が複数種類あるときは、次の順で種類を選ぶ
  1. 最も古い注文の中で杯数が最も多い種類
  2. 同数なら、他の注文の未対応杯数が最も多い種類
  3. それも同数ならメニュー順で先の種類
- 選ばれなかった種類は通常時の決め方、または次の補充に回る（次の補充時点でも最も古い注文であれば、再び優先の対象になる）
- 空き枠がない間は割り込まない。次に枠が空いた補充のときに適用する
- 判定はサーバー（OrderDO）の時刻で行う。注文時刻は JST の文字列のため、JST として解釈する

---

## 消費

抽出開始のとき、次の順でエントリーを 1 件消費する（該当するものを抜き、後ろを詰める）。

| 開始した内容 | 消費するエントリー |
|--------------|--------------------|
| 一致するエントリーがある | 一致するもののうち、1 番目 → 2 番目 → 3 番目の順で最初のもの |
| 一致はないが、同じ種類のエントリーがある | 同じ種類のもののうち、1 番目 → 2 番目 → 3 番目の順で最初のもの |
| 同じ種類のエントリーがない | 消費しない |

- 提案と杯数が違った場合の差分や、同じ種類のエントリーがない場合の抽出分は、補充時の未対応杯数の再計算で自動的に反映される
- 消費後、補充を行う

---

## 取消

### 抽出の取消

- 取り消された抽出中の杯は未対応杯数に戻る（再計算で反映）
- 補充を行う

### 注文の取消

```
取消後、メニューごとに「キューにある杯数の合計」と「未対応杯数（注文数 − 完成 − 抽出中）」を比べる。
キューの方が多ければ、その差の杯数だけ、そのメニューの末尾のエントリーから 1 杯ずつ減らす。
0 杯になったエントリーは削除し、後ろを詰める。キューの方が多くなければ変更しない。
```
