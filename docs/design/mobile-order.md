# モバイルオーダー設計検討書

## 概要

店舗に設置した QR コードを来店客が自身のスマートフォンで読み取り、メニューの選択と注文内容の送信を行う機能を追加する。
注文後は紙のレシートの代わりとして、注文番号・注文日時・商品名と数量・注文状況をブラウザに表示する。

本資料は、合意済みの方針と残る確認事項を整理する設計書である。未決定事項は合意後に実装仕様へ置き換える。

## 確定している前提

- オンライン決済は実装しない
- 支払いが必要な場合は店舗で現金等を受け取る
- 客は店舗ごとに発行した固定の QR コードからアクセスする。営業日ごとには発行し直さない
- 紙のレシートを必須とせず、ブラウザに紙レシートと同じ内容の注文控えを表示する
- 客のログインは要求しない
- モバイル注文も既存の注文・抽出管理へ連携する
- モバイル注文は、店頭での会計完了後に抽出待ちキューへ投入する
- スタッフ向け注文画面に、モバイルオーダー会計用の一覧・操作を追加する
- スタッフが支払完了操作を行ったことを、会計完了の判定とする
- 会計待ち注文は既存の `orders` とは別テーブルに保存し、会計完了時に `orders` へ登録する
- 会計待ちの時点で既存の店頭注文と共通の連番から受付番号を確保し、会計後も同じ番号を使う
- 会計待ち注文は自動失効させず、支払完了またはスタッフによる取消まで一覧に残す
- 前の営業日の会計待ち注文は翌日以降も記録を残す。残った注文の確認・取消はスタッフが手動で行い、日付による自動失効や会計制限は設けない
- 会計完了時刻を抽出順の基準とし、会計後は店頭注文と同じ優先度で扱う
- モバイルオーダー会計画面に受付停止・再開の操作を設け、混雑時や営業終了時にスタッフが新規モバイル注文を止められるようにする
- `/order` にモバイルオーダー会計ページへの遷移ボタンを設け、遷移先で支払完了・会計待ち取消を操作する
- 1注文の合計杯数が10杯以上の場合は、いたずら対策として注文を受け付けない（最大9杯）
- 注文送信後、客自身による取消は許可しない
- 注文送信後、客自身による注文内容の変更も許可しない
- 注文後の待機画面は [`mobile-order-waiting-mockup.html`](./mobile-order-waiting-mockup.html) のデザインを採用する

## 確定フロー

### 会計後に抽出待ちへ進める

```text
QR 読取 → 商品選択・注文完了 → 会計待ち画面 → 店頭会計
        → スタッフが支払確認 → 抽出待ち → 受け取り
```

モバイルからの注文完了時点では会計待ちとし、客は画面を会計係へ提示する。スタッフ向け注文画面のモバイルオーダー会計欄で支払完了操作を行った時点を会計完了とし、その注文を抽出待ちキューへ投入する。会計係による商品の再入力は行わない。

#### 技術的なメリット

- 未払い注文が抽出キューへ入らず、いたずら注文による抽出を防ぎやすい
- 抽出対象は支払い確認済みという明確な条件を持てる
- 会計待ち注文を抽出用の `orders` から分けて管理できる
- 抽出開始後の未払い状態を考慮しなくてよい
- 会計時にスタッフが商品・数量・合計金額を確認できる
- 商品の選択と数量入力は客が済ませるため、会計係による再入力を省略できる

#### 技術的なデメリット

- 会計待ちと会計完了の2段階の状態管理が必要
- 客画面と会計画面を同期し、支払確認後に自動で抽出待ち画面へ切り替える必要がある
- スタッフが支払確認を押し忘れると、支払い済みでも抽出キューへ入らない
- 会計操作の二重送信により抽出対象化が重複しないよう、原子的な確定処理が必要
- 来店しなかった会計待ち注文は、スタッフが取り消すまで一覧に残る
- 客と会計対象を対応付けるため、確認番号または確認用QRの提示が必要
- 会計列が混雑している場合、会計完了まで抽出を開始できない

### 設計判断

注文完了時点では抽出キューへ投入しない。会計完了を条件にすることで、未払い・いたずら注文が抽出されることを防ぐ。会計待ち時間と抽出待ち時間は並行しないため、モバイルオーダーの主な効果は、客自身による事前の商品選択と、会計係による商品入力の省略となる。

## 推奨するデータモデルの考え方

### 会計待ちと抽出・提供の状態を分離する

オンライン決済を行わなくても、「代金を受け取ったか」はシステム上の状態として必要になる。既存の `orders.status` は抽出・提供の進行状態なので、支払い確認に流用しない。

採用する状態：

```text
mobile_order_requests.status: awaiting_payment | paid | cancelled
orders.status:                pending | brewing | ready | completed | cancelled
```

- `awaiting_payment` の間は `orders` を作らず、抽出対象に含めない
- スタッフの支払完了操作でリクエストを `paid` にし、同じ受付番号の `orders` と `order_items` を作る
- 会計待ちの取消はリクエストを `cancelled` にする。`orders` は作らない
- 会計後の提供・取消は既存の `orders.status` で管理する。支払済みの記録は `paid` のまま残す
- 無料提供をモバイル注文で扱うかは別途決める。店頭注文の `isFree` を会計待ちの取消や未払いと混同しない

### 会計待ち注文の管理

モバイルで送信された注文は、支払い前でも客の待機画面とスタッフ向け注文画面の両方から参照できるように保存する。ただし、会計完了までは抽出対象に含めない。

会計待ちは `mobile_order_requests` と `mobile_order_request_items` に保存する。支払完了後だけ既存の `orders` / `order_items` に登録する。次の条件をサーバー側で保証する。

- `awaiting_payment` のリクエストはDOの注文一覧へ渡さず、抽出対象にも含めない
- 支払完了操作ではリクエストの状態変更と `orders` / `order_items` 作成を同じD1 transactionで確定する
- 同じリクエストに対して支払完了操作が再送されても、同じ `orders` を使い、抽出対象化を重複させない
- 客の待機画面に表示する受付番号は注文送信時に発行し、会計後も変更しない

テーブル案：

```text
mobile_order_requests
- id
- public_token
- business_date / event_id
- order_number
- status: awaiting_payment | paid | cancelled
- paid_at
- accepted_order_id
- idempotency_key
- created_at / updated_at

mobile_order_request_items
- id
- request_id
- menu_item_id
- item_name_at_order
- unit_price_at_order
- quantity
```

会計時に作る `orders` には、元のリクエストを示す `mobile_request_id`（店頭注文ではNULL、一意制約付き）を追加する。`accepted_order_id` と併せ、同じ会計待ちリクエストから通常注文を重複作成しないための紐付けに使う。`mobile_order_requests.public_token` と `idempotency_key` にも一意制約を設け、公開URLの重複と注文送信の再試行による二重受付を防ぐ。

受付番号は店頭注文と同じ `order_number_counters` から採番し、`(business_date, order_number)` を会計待ちテーブル内でも一意にする。会計時にその番号を `orders.order_number` へ引き継ぐ。会計待ちの取消や送信失敗で番号に欠番が生じることは許容する。抽出順は番号ではなく会計完了時刻で決める。

`orders.mobile_request_id` の一意制約と状態の条件付き更新で二重登録を防ぐ。注文時の商品名・価格と注文送信時刻は会計待ちテーブルに保持する。客の控えには紙と同じ商品名・数量・日時を表示し、保存した価格はスタッフの会計確認に使う。

### 新規モバイル注文の受付状態

受付中／受付停止中は注文ごとの `status` ではなく、店舗・営業日ごとの運用状態としてD1に保存する。テーブル案は `mobile_order_acceptance(store_id, business_date, is_accepting, updated_at)` で、`(store_id, business_date)` を一意にする。行がない営業日は停止中として扱い、前日の受付中状態を引き継がない。開店時にスタッフが会計画面の「受付再開」を押して当日の受付を始め、混雑時や営業終了時には「受付停止」を押す。開店時刻による自動開始や前夜のD1更新は行わない。

受付停止・再開の確定後にスタッフ画面とQR入口の表示を更新する。ただし表示の更新だけでは止められないため、注文作成APIはD1内で「その店舗・営業日が受付中」という条件付きでリクエストを保存する。停止更新と新規注文が競合した場合、D1で先に確定した操作を優先する。注文確定ボタンを押しただけで保存前だったものは、停止が先に確定すれば受け付けない。すでに受け付けた注文の同じ `idempotency_key` による再送は、停止後も新規作成せず元の注文結果を返す。

スタッフ操作は状態を反転する「トグル」ではなく、「停止に設定」「受付中に設定」という明示的な更新にする。応答だけが失われても再実行で逆の状態にならないようにし、操作後はD1の最新状態を読み直す。

### 支払完了時のD1・DO反映順と失敗時の復旧

既存の店頭注文作成は、D1登録後のDO通知が失敗した場合にD1注文を削除する。一方、既存のDO内の状態更新は、D1を更新してからDOメモリを更新・WebSocket通知する。支払確認後は実際に受け取った代金の記録を削除して巻き戻せないため、後者に合わせる。

1. `/order` 配下の会計操作から、その営業日のOrderDOへ支払完了を依頼する。
2. DOがD1でリクエストの `awaiting_payment → paid` と、同じ受付番号を持つ `orders` / `order_items` の作成を1トランザクションで確定する。具体的な条件付き処理は下記のとおり。`orders.created_at` には会計完了時刻を、既存注文と同じ日時形式で設定し、抽出順に使う。注文送信時刻はリクエスト側に保持する。
3. D1成功後にDOの注文一覧へ反映し、スタッフ画面へ通知する。客画面はD1の状態を再取得して更新できるようにする。
4. D1成功後にDOへの反映や応答だけが失敗した場合、会計操作の再送では `paid` と既存の `accepted_order_id` を読み、同じ注文をDOへ反映し直す。新しい注文・受付番号は作らない。DOの再起動時もD1の有効な注文から状態を復元する。

会計確定では新しい注文IDを用意し、次のSQLを1回のD1 `batch()` に入れる。各SQLの条件はアプリ側の事前確認だけに依存させない。

1. リクエストが `awaiting_payment` で、送信先OrderDOの営業日とリクエストの営業日が一致する場合だけ、`INSERT ... SELECT ... WHERE status = 'awaiting_payment' AND business_date = :requestBusinessDate` で `orders` を作る。`mobile_request_id` にはリクエストIDを設定する。日付が前営業日でも自動では拒否せず、残った注文の扱いはスタッフが判断する。
2. その新しい注文IDの `orders` が実際に存在する場合だけ、会計待ちの商品から `order_items` を作る。商品が0件のリクエストを会計確定しないよう、受付時と会計時に検証する。
3. その新しい注文IDの `orders` が存在し、リクエストがまだ `awaiting_payment` の場合だけ、リクエストを `paid` に更新し、`accepted_order_id` と `paid_at` を記録する。

`batch()` はSQLエラーなら全体をロールバックするが、条件不一致による更新・挿入0件はエラーにならない。正常終了後もリクエストをD1で読み直し、今回の注文IDで `paid` になった場合だけ新規確定として扱う。すでに別の注文IDで `paid` なら既存の `accepted_order_id` の注文を返してDO反映だけ再試行し、`cancelled` なら会計を拒否する。`awaiting_payment` のままなら異常として通知し、抽出対象に入れない。

会計待ちの取消も同じ営業日のOrderDOを通す。支払完了と取消は、状態確認からD1への確定までDO内で直列化し、取消側も `awaiting_payment → cancelled` の条件付き更新で競合を検出する。取消が先に確定した場合は注文を作らず、支払完了が先に確定した場合は会計待ち取消を拒否して既存の注文取消フローへ案内する。

D1で `paid` が確定した後にDO反映が失敗しても、支払確認を取り消したり、会計待ちへ戻したりしない。会計画面には「支払記録済み・注文反映を再試行」と表示し、代金をもう一度受け取る操作と区別する。DOが稼働中のままなら再送で反映し、DO再起動時はD1から復元する。

### 注文時点の商品名と価格を保存する

現在の `order_items` はメニューIDと数量を保持している。メニューマスタの変更後も客向け控えの商品名とスタッフ向け会計金額が変わらないよう、次のスナップショットを注文時に保存する。

- 注文時の商品名
- 注文時の単価
- 数量
- 必要なら税率・税区分

合計金額は必ずサーバー側で再計算し、クライアントから送られた商品名・価格を信用しない。

## 決済なしでも決める必要がある事項

### 1. QRコードと営業単位

- QRは店舗ごとに固定で発行し、営業日ごとには差し替えない
- 1店舗のみか、将来複数店舗を扱うか
- QRからテーブル・受取場所を識別するか
- 受付停止中は、QRから画面を開いても新規注文を確定できない旨を表示する。開店前・営業終了後もスタッフが停止に設定する運用とする
- QRの紛失・流出時に無効化、再発行できるか
- 同じQRを翌日も使う。注文の営業日はQRではなくサーバーで決める

QRには予測可能な営業日や内部IDを直接載せず、推測困難な公開トークンを載せる。サーバー側でトークンから現在有効な店舗・イベントへ解決し、クライアントから送られた `businessDate` を信用しない。

受付可否は店舗・営業日ごとの永続データで管理し、表示用の客画面だけでなく注文作成APIでも確認する。新しい営業日は停止中から始め、スタッフが会計画面のボタンで再開する。停止・再開は新規注文の受付だけを切り替え、既存の会計待ち・抽出待ち・受取可能な注文の表示やスタッフ操作は止めない。

### 2. 注文の成立条件

- 客の送信時点で会計待ち注文として保存し、受付番号を発行する
- スタッフが支払完了操作を行った時点で会計完了とする
- 会計完了後に抽出待ちキューへ投入する
- 会計後は店頭注文と同じ優先順位とし、会計完了時刻で並べる
- スタッフが会計画面で受付を停止・再開する。営業終了時には停止を操作し、時刻による自動停止は初期実装に含めない
- 停止ボタンを押した瞬間ではなく、停止処理がD1で確定した時点から新規注文を拒否する。直前に確定した注文は有効な会計待ち注文として扱う

前の営業日に作られた `awaiting_payment` は自動失効させず、スタッフ用一覧に営業日を明示して残す。日付だけで支払完了を制限せず、残った注文はスタッフが手動で確認・取消する。会計と取消の処理はリクエストが属する営業日のOrderDOへ送る。

### 3. 注文状態と画面遷移

客に見せる状態は次のように扱う。

```text
商品選択中
→ 内容確認
→ 会計待ち
→ 抽出待ち
→ 受取可能
→ 受取済み
```

- `mobile_order_requests.status = awaiting_payment` は「会計待ち」とする
- 会計後の `orders.status = pending`・`brewing` はどちらも「抽出待ち」とする
- `orders.status = ready` は「受け取り可能」とする
- 会計前後を問わずスタッフにより取り消された場合は「注文は取り消されました。スタッフにお声がけください」と表示し、理由は推測して表示しない
- 取消済み・受取済みの注文は表示中の待機画面ではその状態を示し、その後同じ端末でQRを再読込した場合は保存済みの公開トークンを削除して客向けメニューを表示し、次の注文を可能にする
- 営業終了時も、既存注文の待機画面は各注文の状態に従って表示する

### 4. 注文控え画面

紙レシートと同じ注文内容として、受付番号、注文送信日時、商品名と数量を表示する。無料注文を扱う場合のみ、紙と同じ無料表示を付ける。現行の紙レシートには単価・小計・税額・合計金額は載らないため、客向け注文控えにも追加しない。金額は会計画面でスタッフが確認する情報として別に扱う。

待機画面の進行状態と「レジまでお越しください」などの案内は、紙レシートと共通の注文内容の上に表示する。注文内容は公開トークンURLから再取得し、同じ端末では店舗トークンごとの `localStorage` に保存した公開トークンから再表示する。

法的・会計上の正式な領収書として扱うかは、店舗側の運用確認が必要である。正式な領収書ではない場合は、誤解を避けるため画面上の名称を「注文控え」または「ご注文内容」とする。

### 5. 再アクセスと公開トークン

ログインを要求しないため、注文状況を閲覧するための推測困難な公開トークンを注文ごとに発行する。

- URL例：`/mobile/orders/{publicToken}`
- 内部の注文IDや当日連番だけでは閲覧させない
- 送信前に `idempotencyKey` と注文内容を店舗ごとの `localStorage` に保存する。応答が不明なまま再読み込みした場合は同じ内容・キーで結果を確認し、その間は内容変更を許可しない
- 成功応答を受けたら保存内容を公開トークンに置き換え、`/mobile/orders/{publicToken}` に遷移する。同じ端末でQRを再読込したときも、その注文控えへ戻す
- 別端末への引き継ぎを許可するか
- 閲覧トークンの有効期限
- 注文完了後にどの期間まで閲覧可能にするか

### 6. 二重注文と再送対策

モバイル回線では、送信後にレスポンスだけ失われることがある。注文作成APIは冪等にする。

- 注文確認画面を開いた時点で `idempotencyKey` を生成
- 同じキーによる再送では同じ注文結果を返す
- 同じ商品の複数行は保存時も再送比較時も商品IDごとに合算する
- 送信中は確定ボタンを無効化する
- 二重タップ対策をクライアントだけに依存しない
- 会計待ちから会計完了への更新も一度だけ成功するようにする

### 7. メニュー、価格、売り切れ

- モバイルに表示する商品と店頭商品の範囲
- 売り切れ・販売再開を誰が操作するか
- カート投入後、確定前に売り切れた場合のエラー表示
- 表示中に価格が変わった場合、再確認させるか
- 1注文の合計杯数は最大9杯とする。合計10杯以上は注文確定時に拒否する
- オプション、備考、アレルギー表示の有無
- 画像を使用する場合の容量と通信量

注文確定時に、商品の存在、販売可否、価格、数量上限をサーバー側で再検証する。

### 8. 取消・変更

- 注文送信後、客自身による取消は許可しない
- 注文送信後、客自身による注文内容の変更は許可しない。変更が必要な場合はスタッフに申し出てもらい、スタッフ取消後に新しく注文する
- 会計後は既存のスタッフ取消規則を適用する（`ready` まで取消可、`completed` は不可）
- スタッフ取消時に客画面へ表示する理由
- `ready` のまま受け取られない注文の期限と扱い
- 会計待ちの取消ボタンを会計ページに設け、取消後は支払完了できないようにする
- 会計後の取消時は既存の注文取消処理に従い、抽出キューを再計算する

会計待ちは自動失効させず、スタッフが支払完了または取消するまで残す。取消が必要な場合はスタッフが対応し、客の待機画面には取消操作を表示しない。

### 9. 混雑といたずら対策

店舗QRは撮影・共有できるため、QRを読んだこと自体を来店証明として扱わない。

- 1注文の合計杯数は最大9杯とし、10杯以上はいたずら注文として受け付けない
- 同一IP・端末・公開トークンからの作成頻度制限
- 店舗全体の未処理注文数上限
- 混雑時はスタッフが会計画面から新規モバイル注文の受付を停止し、落ち着いたら再開する
- 店外からの注文を許容するか
- CAPTCHA等を導入する条件
- 不審な会計待ち注文をスタッフが拒否できるか

数量上限は、カート画面の表示だけでなく注文作成APIでも検証する。商品ごとの数量ではなく、カート内の全商品の数量合計で判定する。

### 10. リアルタイム同期と通信障害

- 客画面は既存のスタッフ向けOrderDO WebSocketには接続しない。全注文のスナップショットが配信され、他の注文情報を取得できるためである
- 初回表示では公開トークンの注文控えを取得し、表示中はその注文の状態だけをHTTPで取得する。各取得の完了から5秒後に次を実行し、リクエストを重ねない
- バックグラウンド中は定期取得を止め、画面復帰時に直ちに再取得する
- 定期取得が失敗しても最後に取得できた状態と注文控えを表示し続け、「再接続中」と表示して次回の取得で復旧する。初回取得が失敗して控えがない場合は再試行ボタンを表示する
- 状態更新イベントを取り逃しても、次回の取得で最新状態へ収束させる

### 11. `/order` から開くモバイルオーダー会計ページ

- `/order` に「モバイルオーダー会計」への遷移ボタンを追加する
- 遷移先に会計待ちのモバイル注文を一覧表示する
- 客画面と同じ受付番号で照合する。検索・確認用QRの要否は追加検討する
- 支払完了操作を用意し、その操作を会計完了の判定とする
- 現在の受付中／受付停止中を表示し、確認付きの「受付停止」／「受付再開」ボタンを設ける。操作完了後に表示を更新する
- 受付停止中も既存の会計待ち注文の支払完了・取消は継続できる
- 会計待ち注文を取り消すボタンを設け、取消後は会計待ち一覧から除外する
- 支払完了後は会計待ち一覧から除外し、通常注文として抽出対象にする
- 無料扱いをモバイル注文で許可するか
- 支払確認の取り消しを許可するか
- 複数スタッフが同時に同じ注文を操作した場合の競合処理
- D1での支払完了・通常注文作成を1トランザクションにし、DO反映失敗時は同じ注文を再反映する
- 会計画面の合計は注文時に保存した単価・数量からサーバー側で計算し、客の送信値に依存しない

### 12. 抽出キューとの連携

- 会計完了になった時点から未対応杯数へ含める
- 会計後は店頭注文と同じ優先度とし、会計完了時刻を抽出順に使う
- 同時刻注文の並び順
- 会計完了後の注文をスタッフが取り消したとき、次枠キューを補充し直すか
- 会計待ち注文は抽出数、待ち時間予測、売上集計へ含めない

会計完了後は注文元を区別せず、既存注文と同じ抽出ルールで扱う。受付番号の大小は抽出順を表さない。

### 13. 注文時刻と待ち時間

- 注文送信時刻は `mobile_order_requests.created_at` に、会計完了時刻は `paid_at` と `orders.created_at` に保持する
- 抽出の公平性には会計完了時刻を使う
- 客画面には注文送信時刻を表示する
- 待ち時間表示を行うか
- 表示する場合、単なる目安か保証時刻か

会計待ちの間に採番した番号は変更しない。番号と抽出順が一致しない場合があることを、スタッフ画面の並び順で明確にする。

### 14. セキュリティとプライバシー

- 客画面からスタッフ用APIを呼べない認可境界
- CSRF、入力値検証、レート制限
- 公開トークンをログへ不用意に出さない
- 内部ID、他の注文、当日の注文数を推測できないURL設計
- 氏名、電話番号、メールアドレスを取得する必要があるか
- 取得しない場合でも、IPアドレス等のログ保持期間を決める

受取番号だけで運用可能なら、個人情報は取得しない方が実装・管理ともに単純になる。

### 15. スマートフォン向けUI

- 小さい画面で商品、数量、合計を確認できること
- 戻る操作や再読込で注文が重複しないこと
- iOS Safari／Android Chromeでの動作
- ダークモード、文字サイズ拡大、色覚への配慮
- QR読取後の初回表示速度
- 電波が弱い場所で画像やフォントが読み込めない場合の表示
- 注文確定前後を色だけで区別しないこと

### 16. 運用・監査・計測

- モバイル注文か店頭注文かを履歴で識別できること
- 会計待ち注文作成、支払確認、取消、抽出対象化を監査できること
- エラー率、注文作成失敗、WebSocket切断を記録すること
- モバイル注文数、会計待ち放棄数、取消数を集計できること
- QRの差し替え、営業開始・終了の担当者を決めること

## API境界の案

公開APIとスタッフAPIは分離する。

```text
公開
GET  /mobile/{storeToken}                 メニュー・受付状態
POST /api/mobile/order-requests           会計待ち注文の作成
GET  /api/mobile/orders/{publicToken}     注文内容・最新状態

スタッフ認証必須
GET  /order/mobile-checkout                          会計待ち一覧・詳細
POST /order/mobile-checkout                          支払完了または会計待ち取消
POST /order/mobile-checkout/acceptance               新規受付の停止または再開
POST /api/staff/orders/{id}/cancel                    会計後の注文取消
```

- 公開APIは内部注文IDではなく公開トークンを受け取る
- 商品名、価格、営業日、支払状態をクライアント入力に任せない
- 受付可否はD1を正本とする。停止・再開はスタッフだけが操作し、新規注文の保存時にD1側の条件でも受付中を確認する。停止処理と注文作成が競合した場合はD1で先に確定した側を優先する
- `/order/mobile-checkout` の操作はOrderDOへ転送し、D1確定後にDOメモリとWebSocketへ反映する
- 注文作成時の `idempotency_key` は公開注文APIの再送にだけ使う。全操作共通の `operationId` 基盤は導入しない
- 会計の再送は `mobile_order_requests.id` と `accepted_order_id` で同じ注文を再反映する
- スタッフ向けの支払完了・取消操作にはサーバー側の認証・認可が必要。認証は別ブランチで実装し、モバイルオーダー公開前の必須条件とする（現行のスタッフ画面では未実装）

## 実装手順

以下はこのブランチでの実装順。各段階でテストを追加し、会計待ちの保存から客画面まで縦につながる状態を目指す。認証機能そのものは別ブランチで実装するが、認証なしのスタッフ操作を公開しない。

### 0. 実装前の確認と境界整理

1. 現行の `/order` は店頭注文入力画面、`/cashier` は受渡管理画面である。客向け `/mobile/...` は通常のブラウザ画面として追加し、既存PWAの対象には含めない。スタッフ向け `/order/mobile-checkout` は既存の注文管理PWAのURL範囲内に置く。PWAの範囲は認証ではないため、スタッフ用loader・actionの保護は別ブランチの認証実装と統合してから公開する。
2. 店舗固定QR、前営業日の会計待ちはスタッフが手動で確認・取消、紙と同じ注文控え表示、営業日ごとの受付状態とスタッフによる停止・再開を実装条件とする。当日は停止中から始め、開店時にスタッフが会計画面のボタンで再開する。
3. 採用済みの方針として、D1を会計・注文の正本、OrderDOを稼働中の状態管理・通知担当に実装する。会計確定後のDO反映失敗はD1の同じ注文から再反映し、D1への新規書き込みを繰り返さない。

### 1. D1スキーマとマイグレーション

1. `apps/web/db/schema.ts` に `mobile_order_requests`、`mobile_order_request_items`、`mobile_order_acceptance`、`orders.mobile_request_id` を追加し、Drizzleのマイグレーションを生成する。既存の店頭注文は `mobile_request_id = NULL` のまま使えるようにする。
2. リクエストの状態CHECK、商品数量の正数CHECK、必要な外部キーに加え、`orders.mobile_request_id`、`mobile_order_requests.public_token`、`mobile_order_requests.idempotency_key`、`(business_date, order_number)` の一意制約を定義する。商品スナップショットには注文時の商品名・単価・数量を保存する。
3. ローカルD1へマイグレーションを適用し、既存の店頭注文データが読めること、同一リクエストから通常注文を2件作れないことを確認する。リモート適用はデプロイ手順で別途行う。

### 2. 公開メニューと会計待ち注文の作成

1. QR入口の公開ルートで、その営業日に受け付け可能なメニューをサーバーから取得する。既存の `features/menu/queries.ts` を参考にしつつ、営業日・販売可否をサーバー側で判定する。
2. 注文作成処理で商品ID・数量を再検証し、合計1～9杯のみ受け付ける。名前・価格・合計はサーバーのメニューから確定し、クライアントから送られた金額は採用しない。
3. 注文送信ごとの `idempotency_key` で再送を同じリクエストへ収束させる。新規送信はD1の当日・当該店舗の受付状態が「受付中」の場合だけ保存し、停止処理との競合をD1の確定順で判定する。共通の `order_number_counters` から受付番号を確保し、会計待ちリクエストと商品をD1に保存する。ここでは `orders` を作らず、OrderDOの抽出対象へも通知しない。
4. 応答には注文内容を表示するための推測困難な公開トークンを返す。応答消失後の同じキーでの再送でも、同じ受付番号・公開トークンを返すテストを追加する。

### 3. スタッフ向け会計画面と会計確定

1. 既存の `/order` から会計ページへの遷移を追加し、会計待ち一覧・詳細に受付番号、営業日、商品、数量、合計、送信時刻を表示する。同じ画面に現在の受付状態と確認付きの「受付停止／受付再開」操作を設ける。前営業日の会計待ちも一覧に残し、スタッフが手動で確認・取消する。支払完了と会計待ち取消は別操作として、二重押下を防ぐ。
2. 支払完了と取消の要求を営業日単位のOrderDOへ渡し、同じリクエストに対する競合を直列化する。DB側でも状態条件と一意制約で防御し、DO内の事前確認だけには依存しない。
3. 支払完了は「`awaiting_payment` の場合だけ通常注文をINSERT → その新しい注文が存在する場合だけ商品をINSERT → 同じ条件でリクエストを `paid` にUPDATE」を1回のD1 `batch()` で実行する。結果が0件でも成功扱いせず、D1の状態を読み直して `paid`／`cancelled`／異常を判定する。会計時刻を `paid_at` と `orders.created_at` に記録する。
4. D1確定後に既存の `OrderDO.newOrder` と同等の処理で注文を一度だけ反映・通知する。DO反映または応答が失敗したらD1の `accepted_order_id` を取得し、同じ注文を再反映する。会計画面では支払記録済みと未反映を区別し、再徴収を促さない再試行操作を表示する。自動再試行の回数・間隔、画面を閉じた後の復旧起点は公開前に決めてテストする。
5. 会計待ち取消は `awaiting_payment → cancelled` の条件付き更新とし、支払済みなら拒否して既存のスタッフ注文取消フローへ案内する。客による取消・内容変更のAPIは設けない。

### 4. 客向け待機画面と再表示

1. 採用済みモックに合わせて、同じ1ページで「会計待ち → 抽出待ち → 受取可能」を切り替える。紙と同じ受付番号・注文送信日時・商品名・数量はD1のスナップショットから表示し、会計前後で番号を変えない。金額は客向け控えに載せない。
2. 公開トークンを使った取得APIで、支払前はリクエスト状態、支払後は紐付く `orders.status` を返す。受付番号だけでは取得できないようにし、公開トークンをログに出さない。
3. 初回表示と再読込時には必ず最新状態を取得する。表示中は公開トークンでその注文の状態だけを取得し、各取得の完了から5秒後に再試行する。非表示中は定期取得を止め、再表示時に直ちに取得する。スタッフ向けOrderDOのWebSocketは他の注文も配信するため、客画面からは接続しない。定期取得の失敗時も最後に取得できた状態と注文控えを保持し、次回の取得で回復させる。初回取得に失敗した場合は再試行ボタンを表示する。
4. `awaiting_payment` は「会計待ち」、会計後の `pending`・`brewing` は「抽出待ち」、`ready` は「受け取り可能」と表示する。スタッフ取消時は「注文は取り消されました。スタッフにお声がけください」、`completed` は「受取済み」と表示する。取消済み・受取済みの注文は、同じ端末でQRを再読込した場合に保存済みトークンを削除して客向けメニューを表示する。客画面には取消・内容変更操作を表示しない。

### 5. 抽出連携・回帰確認・公開準備

1. 会計待ちは抽出数・注文一覧・売上集計に含めず、支払完了後の通常注文だけを店頭注文と同じルールで扱う。抽出順は会計完了時刻とし、同時刻の並びは決定した規則で処理する。
2. 既存の店頭注文、抽出開始・完了、提供、スタッフ取消に回帰がないことを確認する。特に会計待ち取消と支払完了の競合、支払完了の再送、D1成功後のDO反映失敗、DO再起動、客画面の再取得失敗・復旧をWorkersテストで検証する。
3. `apps/web` で型検査・lint・既存テスト・Workersテスト・ビルドを実行する。実機ではQR読取から支払・受取までと、弱い通信環境での再読込を確認する。
4. 公開前に別ブランチのスタッフ認証を統合し、会計画面の閲覧・支払完了・取消を未認証で実行できないことを確認する。D1マイグレーション、QR配布、スタッフ向けの失敗時手順を揃えてから有効化する。

## 最低限の受け入れテスト

- 店舗QRから注文画面を開ける。受付停止・再開操作はスタッフ会計画面だけに表示する
- 受付停止中はQR入口に停止中と表示し、新しい注文の保存をサーバー側で拒否する。既存の待機画面とスタッフ会計操作は使える
- 受付停止と新規注文が競合した場合、D1で先に確定した結果に従う。停止後の同一キー再送は元の注文結果を返す
- 営業日が変わったら前日の受付中状態を引き継がない
- 売り切れ商品を確定しようとすると注文が作られない
- カート内の合計杯数が9杯なら注文でき、10杯以上なら注文できない
- 注文確定ボタンを連打しても注文は1件だけ作られる
- 注文作成後にレスポンスが失われ、再送しても同じ注文番号が返る
- 注文時点の価格が後から変更されても、会計画面で確認する金額は変わらない
- 注文URLを再度開くと最新状態を表示できる
- 注文番号だけでは他人の注文内容を閲覧できない
- 複数スタッフが同時に支払確認しても、抽出対象化は1回だけ行われる
- 会計待ち取消後に支払完了を試みても通常注文と注文商品は作られない
- 支払完了の再送で通常注文と注文商品が二重作成されず、同じ `accepted_order_id` を返す
- 注文商品が0件の会計待ちリクエストは支払完了にできない
- D1で会計完了した直後にDO反映が失敗しても、再送またはDO再起動後に同じ注文を抽出対象へ復元できる
- 会計待ちの取消と支払完了が競合しても、成功するのは片方だけ
- 会計完了前の注文は抽出待ちキューに含まれない
- 支払完了操作後に注文が抽出待ちキューへ入る
- 客の待機画面に取消操作が表示されない
- 客の待機画面に注文内容の変更操作が表示されない
- 取消された会計待ち注文を支払完了にできない
- 会計待ち注文は時間経過だけでは消えず、スタッフが取り消せる
- 前営業日の会計待ちは一覧に残り、スタッフが手動で確認・取消できる。日付だけを理由に会計操作を無効にしない
- 客向け注文控えの注文内容は紙レシートと同じ受付番号・日時・商品名・数量で、金額を表示しない
- 客画面は他の注文を取得せず、表示中の定期取得・再表示時の取得で最新状態へ復元できる
- 注文取消後に抽出キューと客画面の両方が更新される

## 残っている確認事項

1. 注文控えを正式な領収書として扱うか、単なる注文内容確認とするか
2. 受取時に本人の注文であることを何で確認するか
3. 番号が欠番になること、および番号順と抽出順が一致しないことを運用上許容できるか
4. 会計後に取り消した有料注文の返金をどのように記録・案内するか
