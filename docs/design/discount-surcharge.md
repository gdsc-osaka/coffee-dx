# 割引・割増付き注文機能 実装手順書

## 1. 目的

スタッフが `/order` で商品を受け付ける際に、商品ごとの単価を注文単位で変更できるようにする。

想定する操作は次のとおり。

1. 商品カードで商品と個数を選ぶ
2. 商品カードの割引・割増ボタンからモーダルを開く
3. モーダルに現在の単価を表示する
4. テンキー、`-100円` ボタンなどで単価を変更する
5. `+` / `-` ボタンで、その単価を適用する個数を変更する
6. 「完了」でモーダルを閉じ、カートの明細と合計を更新する
7. 注文確定時に、各明細の実際の適用単価を保存する

この機能では、割引ボタンを押した事実やクーポンの利用履歴を別データとして管理しない。`-100円` は入力を容易にするためのUI操作であり、注文に保存するのは最終的な単価だけとする。

## 2. 現状の確認

現状は、メニューの基本価格を `menu_items.price` に保持している。

- `menu_items` は商品名・価格・説明・販売中フラグを持つ
- `orders` は注文番号・状態・無料注文フラグなどを持つが、金額は持たない
- `order_items` は `menu_item_id` と `quantity` だけを持ち、注文時の価格を持たない
- 注文作成時の `CartItem.price` は画面上の計算には使うが、`order_items` には保存していない
- 現在のカート追加処理は `menuItemId` が同じ明細を1行にまとめる
- `/order` は現在 `_customer/home.tsx` に紐づいており、スタッフ認証も未実装である
- `/order` のヘッダーと会計確認画面には、スタッフ向け表示をカウンター越しに見せるための `rotate-180` と、来場者向けの下部表示がある

## 3. 実装方針

### 3.1 商品マスタの価格と注文時価格を分離する

`menu_items.price` は現在の基本価格として残す。注文時には、その時点で実際に適用された単価を `order_items.unit_price_at_order` に保存する。

通常価格の商品も例外なく保存する。

```text
menu_items.price                  基本価格・現在の定価
order_items.unit_price_at_order   その注文に適用された単価
```

これにより、後からメニューの基本価格を変更しても、過去の注文金額が変わらない。

### 3.2 注文単位の割引額は持たない

現時点では次のカラムやテーブルは追加しない。

- `orders.discount_amount`
- `orders.surcharge_amount`
- `is_discounted` のような割引フラグ
- クーポンマスタ・クーポン利用履歴テーブル
- `order_adjustments` テーブル

割引・割増後の単価そのものを `order_items.unit_price_at_order` に保存する。

### 3.3 同じ商品を価格別の複数明細として保存する

同じ商品でも、注文内で異なる単価が適用される場合がある。`order_items` は同じ `menu_item_id` の行を複数持てるようにする。

例: コーヒーAを3個注文し、1個だけ100円引きにした場合。

```text
menu_item_id | unit_price_at_order | quantity
-------------|---------------------|---------
coffee-a     | 200                 | 1
coffee-a     | 300                 | 2
```

合計は `200 * 1 + 300 * 2 = 800` 円となる。

`menu_item_id` 単位での一意制約は設けない。行を識別するのは既存の `order_items.id` とする。

### 3.4 合計金額は明細から算出する

合計金額は次で算出する。

```text
SUM(order_items.unit_price_at_order * order_items.quantity)
```

画面上のプレビューも、サーバー側の注文検証も、この計算方法にそろえる。注文単位の金額カラムを追加するかどうかは、売上集計要件が固まった時点で再検討する。

### 3.5 `/order` は通常向きのスタッフ操作画面にする

`/order` はスタッフが操作する画面なので、画面を客とスタッフで挟んで使う前提を廃止する。

変更後の方針:

- 画面全体を0°（通常向き）で表示する
- `rotate-180` をヘッダー・確認画面を含めて使用しない
- スタッフ向けヘッダーは画面上部に通常向きで表示する
- 商品カードと注文内容は画面中央から上部に配置する
- 合計、注文確認、支払い確定、無料確定、キャンセルなどの操作は画面下部の固定アクション領域に配置する
- 会計確認画面のスタッフ操作を画面上部から画面下部へ移動する
- 客向けの「現金でお支払いください」「FREE」などの表示と、上下二分割レイアウトを廃止する

目標レイアウト:

```text
┌────────────────────────────┐
│ スタッフヘッダー             │
├────────────────────────────┤
│ 商品一覧 / 注文内容           │
│                              │
│ 小計・適用単価・数量          │
├────────────────────────────┤
│ 合計                         │
│ [戻る] [支払い・注文を確定]   │  ← 画面下部に固定
└────────────────────────────┘
```

画面下部の操作領域は、商品一覧や確認内容をスクロールしても押せる状態を維持する。操作領域が内容を隠さないよう、本文側に下部余白を確保する。

### 3.6 非コーヒー商品は同じ商品マスタで管理し、抽出要否を分ける

コーヒー豆・お菓子などを扱うためだけに、別の商品テーブルは作らない。既存の `menu_items` を商品マスタとして使い、商品ごとに抽出が必要かどうかを持たせる。

商品マスタには `fulfillment_type` を追加し、値は `brew` / `direct` とする。既存商品は `brew` として移行する。`direct` の商品は `brew_units` を作らず、ドリップ画面の抽出対象にも含めない。

注文確定時には、商品マスタの `fulfillment_type` を `order_items.fulfillment_type_at_order` にスナップショットする。商品マスタの設定変更によって、過去注文の状態判定が変わらないようにする。

### 3.7 注文状態の意味は支払い状態と混同しない

現在の `orders.status` における `completed` は「支払い済み」ではなく「受け渡し完了」を意味する。`OrderDO` の `close` も `ready` から `completed` へ遷移させる操作である。

そのため、非コーヒー商品の状態は「支払いと同時に商品を渡すか」で決まる。

- 非コーヒー商品のみの注文で、支払い時に商品を渡す: 注文作成時に `completed` とする
- 非コーヒー商品のみの注文で、支払いと受け渡しを分ける: 注文作成時に `ready` とし、受け渡し後に `completed` とする
- コーヒーと非コーヒーの混在注文: 非コーヒー分は抽出不要として扱うが、注文全体はコーヒー分の抽出完了を待って `ready` にする。コーヒーを渡した時点で注文全体を `completed` とする

今回の `/order` では、非コーヒー商品は支払い時にその場で渡す前提とし、非コーヒー商品のみの注文は `completed` とする。この場合、完了済み注文をリアルタイムの会計待ち一覧へ送る必要はない。

コーヒーと非コーヒーを別々のタイミングで渡す部分受け渡しまで必要なら、注文単位の `status` だけでは不足する。その場合は `order_items` 単位の受け渡し状態、またはコーヒー注文と物販注文を別注文番号に分ける設計を改めて検討する。支払い済みと受け渡し済みを別状態として管理する場合は、`paid` / `settled` などの状態追加も候補になる。

## 4. 実装前に解決する問題

以下は、決定済みの前提と、実装開始前に確認する依存事項をまとめたものである。

### 4.1 `/order` のスタッフ認証（別ブランチで実装）

価格をクライアントから変更できるようにすると、未認証の利用者が任意の価格で注文を作成できてしまう。現在 `/order` は公開ルートで、スタッフ認証は未実装である。

この機能では、`/order` にスタッフ認証を追加し、そのままスタッフ用画面として使用する。認証実装自体は別ブランチで行う。

割引・割増機能の実装ブランチでは、次を前提とする。

- `/order` のactionはスタッフ認証済みのリクエストだけを受け付ける
- 認証が未統合の状態で価格変更を本番公開しない
- 認証ブランチとの統合時に、価格変更actionの認可テストを追加する

### 4.2 `-100円` の適用範囲（決定済み）

`-100円` はクーポン利用記録ではなく、モーダル内で単価を入力しやすくするための補助ボタンとする。ボタンの適用範囲は、そのモーダルで編集している商品・個数だけとする。

モーダルで対象個数が1個、入力価格が300円、`-100円` を押した場合は、その1個の単価を200円にする。注文全体の他の商品や、同じ商品の別価格行には影響させない。

`-100円` を何回押せるかは価格入力制限に従う。割引ボタンを押した事実やクーポン利用枚数は保存しない。

### 4.3 モーダルで変更する個数の初期値（決定済み）

商品Aを3個選んだ状態でモーダルを開いた場合でも、変更対象個数の初期値は0個とする。

スタッフが必要な個数だけ `+` で増やす。対象個数が0個のまま「完了」を押した場合は、価格変更なしとしてモーダルを閉じるか、完了ボタンをdisabledにする。どちらにするかはUI実装時に統一する。

### 4.4 複数の価格変更行を作れるか（決定済み）

同じ商品について、次のような3種類以上の価格を許可する。

```text
A 300円 × 1
A 200円 × 1
A 100円 × 1
```

価格変更を繰り返した結果、カート内に価格別の明細行が複数存在できるようにする。異なる価格の行を商品名だけで統合しない。

### 4.5 価格の入力制限（決定済み）

次の制約をUIとサーバーの両方で検証する。

- 価格は整数円
- 0円は許可する
- 負の価格は禁止する
- 割増の上限は設けない
- `-100円` は連続適用可能
- 無料注文は0円の単価として扱える

### 4.6 非コーヒー商品の状態遷移と登録方法

コーヒー豆・お菓子などは既存の `menu_items` に登録する。別の商品テーブルは作らない。

ただし、現在の注文状態はコーヒー抽出を前提としているため、次の属性を商品マスタに追加する。

- `fulfillment_type`（`brew` / `direct`）

非コーヒー商品は `direct` とし、`brew_units` を作らず、ドリップ画面へ表示しない。注文作成時に抽出要否を `order_items` にコピーする。

今回の `/order` では支払い時に非コーヒー商品を渡すため、非コーヒーだけの注文は `completed` とする。支払いと受け渡しを分ける運用へ変更する場合だけ、`ready` を経由する。

コーヒーと非コーヒーを同じ注文に含めた場合は、コーヒーの抽出完了を待って注文全体を `ready` とする。非コーヒーだけ先に渡す部分受け渡しが必要になった場合は、`order_items` 単位の状態、または別注文番号が必要になる。

### 4.7 履歴・レシートでの表示

同じ商品が価格違いで複数行になった場合の表示を決める。

推奨表示:

```text
コーヒーA  300円 × 2
コーヒーA  200円 × 1
```

異なる単価の行を商品名だけでまとめると、金額の根拠が分からなくなるため、少なくともスタッフの履歴では価格違いを分けて表示する。

## 5. 実装手順

### Step 1: データモデルと入力契約を確定する

1. `unit_price_at_order` を「注文確定時の実適用単価」と定義する
2. 同じ `menu_item_id` の複数 `order_items` を許可する
3. `CartItem` を価格別の注文行として扱う
4. クライアントから送信するデータ形式を決める

推奨する送信形式:

```json
[
  { "menuItemId": "coffee-a", "unitPriceAtOrder": 300, "quantity": 2 },
  { "menuItemId": "coffee-a", "unitPriceAtOrder": 200, "quantity": 1 }
]
```

`name` や基本価格はクライアントの値を信用せず、サーバーが `menu_items` から取得する。

### Step 2: D1スキーマを変更する

`order_items` に次を追加する。

```text
unit_price_at_order INTEGER NOT NULL CHECK (unit_price_at_order >= 0)
fulfillment_type_at_order TEXT NOT NULL CHECK (fulfillment_type_at_order IN ('brew', 'direct'))
```

作業内容:

1. `apps/web/db/schema.ts` を変更
2. `pnpm db:generate` 相当のコマンドで migration を生成
3. SQLiteの既存データ移行SQLを確認する
4. 既存注文には、当時の `menu_items.price` をコピーして埋める
5. `menu_items.fulfillment_type` を追加し、既存商品を `brew` として埋める
6. `order_items.fulfillment_type_at_order` を追加し、既存注文を `brew` として埋める
7. ローカルD1へ適用する
8. 本番反映前に既存注文の件数と価格・抽出要否の欠損がないことを確認する

既存の `order_items` に対して後から `NOT NULL` カラムを追加するため、生成されたmigrationがそのまま安全に実行できるか確認する。必要なら、新テーブル作成 → 既存データ移行 → 旧テーブル削除 → リネームの手順に書き換える。

### Step 3: 注文入力のスキーマを変更する

対象: `apps/web/app/_customer/schemas.ts`

1. 送信データに `unitPriceAtOrder` を追加
2. `quantity` は正の整数にする
3. `unitPriceAtOrder` は0以上の整数にする
4. 空配列を拒否する
5. 同じ `menuItemId` が複数行あっても拒否しない

価格変更を許可するルートがスタッフ専用であることを、入力検証とは別に認証で保証する。

### Step 4: 注文作成処理を変更する

対象: `apps/web/app/features/order/actions.ts` と `/order` のaction。

1. `CartItem` に実適用単価を追加する
2. サーバーで全 `menuItemId` の存在を確認する
3. 商品の販売可否をサーバーで確認する
4. 単価・数量を再検証する
5. `orderItemsData` に `unitPriceAtOrder` を含める
6. 同じ商品が複数行ある場合も、行ごとに別IDでINSERTする
7. `orderItemsData` に `fulfillmentTypeAtOrder` を含める
8. `direct` 商品については `brew_units` を作成せず、`brew` 商品だけを抽出処理へ渡す
9. `direct` 商品だけの注文は、支払い時に受け渡す前提で `completed` として作成し、混在注文は `brew` 商品の準備完了を待って `ready` にする
10. `orders` と全 `order_items` を同じbatchで保存する
11. `completed` の非コーヒーだけの注文は、抽出も受け渡し待ちもないためOrderDOへ登録・broadcastしない
12. コーヒーを含む注文は既存どおりOrderDOへ通知する
13. Durable Object通知に失敗した場合の既存ロールバックを維持する

注文確定時の価格は、画面の合計金額ではなく、サーバーが検証した各明細の単価と数量から再計算する。

### Step 5: カート状態を価格別の明細行に変更する

対象: `apps/web/app/_customer/home.tsx` と関連コンポーネント。

現在は `menuItemId` をキーに同一商品をまとめているため、価格変更後も同じキーで上書きしないようにする。

推奨する画面上の状態:

```ts
type CartLine = {
  lineId: string;
  menuItemId: string;
  name: string;
  basePrice: number;
  unitPrice: number;
  quantity: number;
};
```

実装ルール:

- 初回追加時は `unitPrice = basePrice`
- 商品カードの数量表示は、同じ `menuItemId` の全行を合算する
- 通常の `+` は通常価格の行に追加する
- 通常の `-` は通常価格の行から減らす
- 価格変更時は対象個数を通常価格行から分離する
- 同じ商品・同じ単価の行は、必要に応じてまとめてよい
- 異なる単価の行は必ず分ける
- 商品カードには、数量操作とは別に価格変更モーダルを開くボタンを置く
- 商品一覧下部の固定アクション領域から注文確認へ進める

例:

```text
変更前: A 300円 × 3
変更後: A 300円 × 2 / A 200円 × 1
```

合計は既存の `unitPrice * quantity` の集計で計算できる。

### Step 6: 価格変更モーダルを追加する

モーダルの責務は、注文行の単価と対象数量を編集することに限定する。

必要な要素:

- 現在の単価表示
- 数字入力用テンキー
- `-100円` ボタン
- 必要なら `+100円` ボタン
- 対象個数の `+` / `-`
- 「定価に戻す」ボタン（任意だが推奨）
- 「完了」ボタン
- 「キャンセル」ボタン

「完了」時に次を行う。

1. 入力された単価と個数を検証する
2. 対象個数を元の価格行から減らす
3. 変更後単価の行を追加する
4. 変更後のカート合計を再計算する
5. モーダルを閉じる

キャンセル時はカートを変更しない。

### Step 7: 確認画面と注文送信を変更する

確認画面には、価格違いの明細を分けて表示する。確認内容は画面上部から中央に置き、支払い確定などのスタッフ操作は画面下部の固定アクション領域に置く。

```text
コーヒーA  300円 × 2  600円
コーヒーA  200円 × 1  200円
----------------------
合計                 800円
```

送信時には、画面で計算した合計ではなく、価格別の明細配列を送信する。サーバー側で再計算した結果と一致した場合だけ注文を確定する。

確認画面では、客向けの支払い案内や180°回転した操作領域を表示しない。スタッフが通常の向きで、内容確認から確定操作まで同じ画面内で完了できることを優先する。

### Step 8: 履歴・印字・スタッフ画面を対応させる

1. 履歴クエリで `unit_price_at_order` を取得する
2. 履歴の型に単価を追加する
3. 価格違いの同一商品を誤って統合しない
4. レシートに単価・明細金額を表示するか決め、表示する場合は印字データへ追加する
5. ドリップ画面では `brew` 商品だけを表示する
6. 同じ商品IDの注文行が複数あっても、抽出数量を正しく扱う
7. `direct` 商品だけの注文が支払い確定時に `completed` になる
8. コーヒーを含む注文だけが会計画面の `pending` / `brewing` / `ready` に表示される
9. 会計画面の受け渡し操作で `ready` から `completed` へ遷移できる
10. 会計画面・履歴画面で単価変更後の合計を正しく表示する

抽出処理は商品IDと数量を中心に動作しているため、同一商品に複数の価格行があるケースを回帰テストする。

### Step 9: テストする

#### DB・サーバー

- 通常価格の商品が `unit_price_at_order` に保存される
- 変更価格の商品が変更後の単価で保存される
- 同じ商品IDの価格違い行を同時に保存できる
- 0円を許可する場合に保存できる
- 負の単価を拒否する
- 小数や文字列の単価を拒否する
- 価格未指定を拒否する、または基本価格へフォールバックする
- 存在しない商品IDを拒否する
- 販売停止商品を拒否する
- `direct` 商品だけの注文で `brew_units` が作られず、注文が `completed` になる
- `brew` と `direct` の混在注文で、`direct` 商品が抽出待ちとして計上されない
- `brew` と `direct` の混在注文は、`brew` 商品の準備完了まで `completed` にならない
- 注文作成後にメニュー価格を変更しても、過去注文の単価が変わらない

#### UI

- 初回追加時に定価が入る
- 価格変更モーダルを開いたときの対象個数が0である
- `+` / `-` で数量だけが変わる
- `-100円` で入力中の単価が100円下がる
- モーダルをキャンセルすると元のカートに戻る
- 商品A 3個のうち1個だけ価格変更すると、2行に分かれる
- 価格変更後の合計が正しい
- 同じ単価の行をまとめても合計が変わらない
- 確認画面に価格違いの明細が分かれて表示される
- 非コーヒー商品がドリップ画面に表示されない
- 非コーヒーだけの注文が会計係の受け渡し待ち一覧に残らない
- `/order` のすべての表示が通常向きで、180°回転していない
- 注文確認・支払い確定・無料確定・キャンセルが画面下部の固定領域にある
- 商品一覧や確認内容をスクロールしても、下部の確定操作を実行できる
- 客向けの上下二分割表示や支払い案内が表示されない

#### Durable Object・履歴

- 同一商品IDの複数注文行でも抽出数量が二重計上されない
- 注文状態の更新・キャンセルが従来どおり動く
- 履歴で価格違いの明細が欠落しない
- 既存の無料注文が壊れない
- 認証ブランチ統合後、未認証ユーザーが価格変更注文を作成できない

## 6. 実装完了の受け入れ条件

- 商品カードから価格変更モーダルを開ける
- モーダルを閉じると単価・個数・合計が注文画面へ反映される
- 同一商品を異なる単価で複数個注文できる
- 注文確定後、`order_items` に実際の適用単価が保存される
- メニューの基本価格を後から変更しても、過去注文の金額は変わらない
- 注文単位の割引額や割引フラグを使わずに計算できる
- 未認証ユーザーが任意の単価で注文できない
- 既存の抽出・履歴・印字フローが壊れない

## 7. 仕様変更時の再検討ポイント

次の要件が追加された場合は、`unit_price_at_order` だけの設計では不足する可能性がある。

- クーポンの利用枚数や利用者を記録したい
- 1注文につき1回だけ割引したい
- 割引を商品単価ではなく注文全体へ適用したい
- 割引対象商品かどうかをサーバーで厳密に制限したい
- 売上集計で「定価売上」「割引額」「割増額」を分けたい
- スタッフごとの価格変更履歴を監査したい

この場合は、商品・注文・調整額を分ける設計へ拡張し、`order_adjustments` などの導入を改めて検討する。
